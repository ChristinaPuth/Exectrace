## 4. Errors and issues met during M1

The first full test run passed (72 of 72). The problems below were found by
deliberately breaking rules, not by failing tests.

| # | What happened | Cause | Resolution |
|---|---|---|---|
| 1 | Breaking the "page lists both people, so they are co-holders" check still passed every test | No case covered an appointment together with a page listing | Added cases 13 (page lags behind an appointment) and 14 (page lists both) |
| 2 | Breaking "undated articles are weak" appeared to pass every case | Fault in the mutation script itself: it built claims with the unbroken class, so breaks inside it had no effect | Script now rebuilds each claim with the broken version |
| 3 | Breaking "snippets cannot report a departure" passed every case | No case had a role known only from a snippet | Added case 19 |
| 4 | Future appointments had a unit test but no worked case showing the holder stays current | Gap found in review on 2026-11-11 | Added cases 29 and 30 and a mutation |
| 5 | After the announced-role change, 2 tests failed (`2 failed, 75 passed`) | They expected a future appointee to have no role; the appointee is now `announced` | Expectations updated to the agreed behaviour |
| 6 | Mutation check reported `NOT APPLIED` for one break (18 of 19) | The line it replaces had changed, so the break no longer matched the code | Break updated to the new line; 19 of 19 |
| 7 | Co-CEOs listed on the company's own page were flagged as a conflict | Rule 7 looked only at the number of holders, never at the titles. Found in review on 2026-11-12 | Shared titles on the live page now clear the conflict (cases 16, 40 to 45) |
| 8 | Worked cases did not check the conflict flag, so issue 7 passed every case | Cases compared only status, rule and employment | Every case now also states which roles must be flagged; cases 5, 6 and 15 had their flags written down |
| 9 | Breaking "'co-' must be followed by a role word" passed every case (22 of 23) | No case had two people with "Co-founder and CEO" | Case 44 changed to that situation; 23 of 23 |
| 10 | In manual testing the conflict messages were read as "CTOby" and "CEOby" | The messages themselves contain the space (checked in the code, the log and the database). The display tool printed them at the end of a very long line, which a terminal wraps exactly at that space | Conflict messages are now printed on their own line; `test_conflict_messages_are_cleanly_worded` checks every message for run-together words |

Design gap closed while writing the rules: applied literally, "the live page
shows someone else" would have marked a person named in a *newer* news article
as former. The rule now ends a role that way only when the person has no
recent reliable source; otherwise both stay and the conflict is flagged
(case 15).

## 5. Interpretations added to the spec

The clarifications needed to turn SPEC 3.6 into code are listed in SPEC
section 3.6 under "Clarifications fixed during M1".

Added on 2026-11-12, as agreed in review (SPEC 3.6, rule 0 and rule 1):

- **Announced roles.** An appointment that has not taken effect gives the
  appointee a role with status `announced`. It is never `current`, is not in
  `current_leadership`, and does not make the person a current employee.
- **No date given.** "Will become CFO" and "will step down" are never dated
  by their publication date. An undated appointment takes effect when a later
  source shows the person in the role; an undated departure when a later
  company source says it happened or a successor takes over.
- **Successor shown.** A current role links to the announcement of its
  successor. This is a note: it is not a conflict and does not end the role.
- **Stale announcements.** After 12 months without confirmation an undated
  appointment becomes `unverified` and an undated departure is ignored. The
  claims themselves are never deleted or changed.

- **Shared roles.** Two or more people whom the company's live page lists
  with a shared title ("Co-CEO", "Joint CEO") are all `current` with no
  conflict. Every holder must have such a title on the page; otherwise the
  conflict stays. No schema change: the title wording decides.

Schema additions: `claims.effective_pending`, `roles.starts_on`,
`roles.successor_claim_id`, `roles.ended_by_claim_id`, the status value
`announced`, and four view columns (`starts_on`, `successor`,
`successor_starts_on`, `successor_source_url`).

## 6. Not covered in M1

- **Real data.** The rules run on hand-written claims. Real claims arrive in M3.
- **Title normalization.** The rules trust each claim's level, department and
  canonical role. Assigning those is M3.
- **Verification results** (`last_verified_at`) are M4.
- **Read-only guard for the chat agent** is M5. The views exist; the guard does not.
- **Setting `effective_pending`** is M3. Until extraction tells "will become"
  from "has become", the rule is proven only on hand-written claims.
- **A future return to a role the person already held.** If X left as CTO and
  is announced to return, the existing `former` row is kept and no
  `announced` row is added.
